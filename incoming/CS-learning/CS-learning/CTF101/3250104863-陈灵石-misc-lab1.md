## fixpoint

先看看代码逻辑，大概就是把标准 base64 的字符表改成了 flag，然后要逆推这个表。判断逻辑是多次编码的结果前 1000 个字符与再次编码的前 1000 个字符相同。只要把 fixed_point 再编码一次就能推出确实的 flag。

![[ctf101-misc1-4.png]]

然后通过已经给出的 flag 部分填充没有还原的部分

flag: `bctf{DEPCmQqklUgj5yNBA93IHMYaVFiXedxroKsh4GuSvJW72OzwLR6Z8p01nT}`

base64 编码过程： 3个字节的 `3*8=24` bit 当作 `4*6=24` bit，分成 4 个 6 bit 块，分别看作二进制数索引，转化成映射表中相应位置的字符，就把三个字节变成 4 个可见字符。

如何从 fix point 建立“6-bit 索引到自定义字符”的对应关系:

```python
indices = [
    a >> 2,
    ((a & 0b11) << 4) | (b >> 4),
    ((b & 0b1111) << 2) | (c >> 6),
    c & 0b111111,
]
```

把三个字节 a, b, c 通过位运算拆分成 4 个对应到自定义字符组的索引（6 bit）

```python
index = indices[offset]
recovered[index] = output_char
```

recovered 是待还原的自定义字符组，output_char 是目前遍历到的 fix_point  的字符。

先看下协议分级，全部是 HTTP，而且基本都是 POST，过滤出来一个个看。(`http.request.method == "POST"`)

![[ctf101-misc1-5.png]]

看起来很正常的 guest 登录。继续往后看

![[ctf101-misc1-6.png]]

- 请求和响应之间用 `tcp.stream` 关联，比如上图分别是 1 和 2 的完整对话。

非常典型的 sql 延时注入，目的是猜 secret_value 的长度，后面应该就是逐字节偷取，不出意外就是 flag 了。

解码还原一下： `username=admin' AND IF(LENGTH((SELECT secret_value FROM secret_store LIMIT 1))>32,SLEEP(0.8),0)-- -&password=incorrect`

满足长度大于 32 则延时 0.8，看下时间差触发了延时。

相同方法看后面继续的二分法，确定长度是 37。

然后依旧是延时注入猜出每个字符的 ASCII，一个个还原：

比如第一个请求： `username=admin' AND IF(ASCII(SUBSTRING((SELECT secret_value FROM secret_store LIMIT 1),1,1))>79,SLEEP(0.8),0)-- -&password=incorrect`

最后得到 flag: `ZJUCTF{1_10v3_Ar1har4_Nan4m1_for3ver}`
