### 分析

目标是获取最开始注入的环境变量，及获取 `/flag_随机数` 文件的内容。文件名包含随机数不得而知，而且存放在系统根目录，无法在 Web 根目录直接访问。`index.php` 直接通过 `system()` 执行系统命令，导致容易跨越 PHP 到 Shell 的信任边界？那么只要通过注入 `index.php` 来执行系统操作拿到 flag。

`index.php` 通过正则表达式黑名单防御攻击，只需要选择黑名单中遗漏的字符组成的命令即可。已经有了 `echo `，在当前页面输出文件内容不太方便。不妨嵌套一层，把命令写入一个 php 文件，再由该文件执行 shell 命令 `cat /flag*` 得到 flag。

payload: `/?hello=%27<?=system("cat%20/flag*")?>%27%20>%201.php`

（即 `/?hello='<?=system("cat /flag*")?>' > 1.php`）

此时只要 `curl .../1.php` 理论上就能拿到 flag。

### 总结和问题

遇到的问题： 再本地测试时总是失败，但相同的 payload，在线环境就没问题，查了一下似乎是因为 `php:8.3-apache` 镜像中 `/var/www/html` 目录的默认拥有者是 `root`，权限是 755，导致普通用户没有写权限，`1.php` 就会创建失败。

## PPT 54 页

![[ctf101-web1-3.png]]

flag: `flag{JTTP_3.0_is_on_the_horizon_e98f4f61f7ed}`

阅读分析业务逻辑，发现后端逻辑中只要请求的路径匹配 `/flag` 就能打开 flag 文件拿到 flag。但前端校验中限制 `/flag` 返回 403 blocked。目标就是绕过前端的校验，同时让后端解析出的路径与 `/flag` 匹配。

仔细分析前后端的校验逻辑，前端直接校验路径是否严格等于 `/path`，然后序列化构建一个 JSON 格式（seq），后端接收 JSON 对象并通过 `json.loads(line)` 解析，然后校验 `req["path"]`。中间经过了序列化后再提取的过程。序列化过程是简单的字符串替换，通常就存在注入漏洞。结合 `json.loads()` 对于重复字段保留最后一个的机制，就可以进行 JSON 注入。

payload: `/x","path":"/flag`

payload 与 `/flag` 不相等，成功绕过前端校验，序列化过程中经过字符串替换，得到的 JSON 为：

```json
{"method":"GET","path":"/x","path":"/flag","headers":"..."}
```

`json.loads(line)` 解析到的 `path` 就被覆盖为了 `/flag` ，符合打印 `flag` 的逻辑，成功拿到 flag。

总结： 这道题主要是由于不安全的数据序列化，前后但解析差异导致的注入漏洞。避免这个漏洞可以使用更加安全的序列化方法（`json.dumps()` ，自动转移字符，而非直接替换）。或者让  `json.loads()` 的逻辑更严谨（？）。从信任边界的角度来看，后端信任了前端的解析，所以关键只需要绕过前端校验，就相当于跨越到了目标的信任边界里。所以后端应该要对前端发送的内容进一步校验。

分析业务代码 `app.py` 尝试能访问 `/flag` 的方法。

接收 `POST` 请求时，包含两个参数 `zipfile` 和 `path`。

代码对 `path` 参数进行校验。如果其真实物理路径（`os.path.realpath`）等于 `/flag`，会被拦截。因此无法通过常规的目录穿越来读取 `/flag`。

使用 `subprocess.run` 执行了 `unzip`、`cp` 和 `zip` 命令，并且开启了 `shell=True`。可能存在命令注入？但所有外部传入的变量（`upload_zip`、`tmp`、`src`、`dst`、`archive`）都用了 `shlex.quote()` 进行转义。

再找业务逻辑漏洞：

执行了三个命令： `unzip -q {upload_zip} -d {tmp}`、`cp -- {src} {dst}`、`zip -qr {archive}`

`zip` 命令没有 `-y` 参数，在遇到符号链接时会追踪链接读取真实文件的内容。`unzip` 命令在遇到压缩包内的符号链接时，默认会将其原样解压出来。

构造利用链： 在本地伪造一个指向 `/flag` 的软链接并带 `-y` 保留链接打包进 ZIP。上传后，服务器 `unzip` 原样解压出来，再用没有 `-y` 的 `zip` 重新打包，就会读取到真正的 `/flag` 内容，最后通过下载附件把内容返回。

按照利用链构造 payload 即可。

最小修复：

![[ctf101-web1-7.png]]

修复思路：让签名校验看到的 JSON 和后续执行使用的 JSON 完全一致。

原漏洞来自重复 JSON 键解析差异：

```
public_view = first-wins
render_view = last-wins
```

攻击者可以让校验阶段看到安全字段：

```
printProfile=counter-copy
printer=thermal-standard
```

但渲染阶段看到危险字段：

```
printProfile=clearing-batch
printer=line-printer
driverProgram=/usr/bin/base64
driverArgument=/flag
```

修复方式：

```
public_view = json.loads(payload_text, object_pairs_hook=reject_duplicate_keys)
render_view = public_view
```

也就是：

1. 解析 JSON 时发现重复键就拒绝。
2. 校验和执行共用同一个解析结果。

这样签名对象不再存在两种视图，重复键绕过失效，危险 `printPlan` 无法进入结算渲染链。
